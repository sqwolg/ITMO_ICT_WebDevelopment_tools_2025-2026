# Архитектура решения

## Общая схема

Лабораторная работа строится вокруг разделения ответственности между сервисами.

```text
Клиент
  |
  v
FastAPI todo_app
  |        \
  |         \ синхронный HTTP
  |          v
  |      web_parser
  |
  v
PostgreSQL
```

Для фоновой обработки добавляется очередь:

```text
Клиент -> FastAPI -> Redis -> Celery worker -> web_parser
   ^                                         |
   +------------- task_id / result ----------+
```

## Основное приложение

`todo-app` отвечает за бизнес-логику:

- регистрацию и авторизацию пользователей;
- работу с todo;
- обращение к parser-service;
- создание todo на основе результата парсинга;
- постановку задач парсинга в очередь.

FastAPI-приложение создается в `todo_app/main.py`, а маршруты подключаются через общий router. Для хранения данных используется PostgreSQL и Tortoise ORM.

## Сервис парсера

`web-parser` выделен в отдельное приложение. Его задача узкая: принять URL, загрузить страницу, найти тег `<title>` и вернуть результат в JSON.

Такое разделение полезно, потому что парсинг может быть долгой операцией. Отдельный сервис можно развивать, перезапускать и масштабировать независимо от основного API.

## Синхронный и асинхронный сценарии

Синхронный сценарий проще: FastAPI отправляет HTTP-запрос в `web_parser` и ждет ответ. Этот подход подходит для коротких операций.

Асинхронный сценарий нужен для долгих задач: FastAPI быстро возвращает клиенту `task_id`, а Celery worker выполняет парсинг в фоне. Redis используется как очередь и как хранилище результата.

## Почему используется Docker Compose

Docker Compose позволяет описать всю систему в одном файле и запускать ее одной командой. Это особенно важно, когда приложение зависит не только от Python-кода, но и от PostgreSQL, Redis, сети между контейнерами и переменных окружения.
