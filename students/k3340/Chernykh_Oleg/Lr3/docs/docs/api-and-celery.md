# API и очередь

## Синхронный вызов парсера

Основной backend отправляет URL в сервис `web_parser` по HTTP. Типовой сценарий:

1. Клиент отправляет URL в `POST /parser/parse`.
2. FastAPI проверяет пользователя.
3. Backend делает POST-запрос в `http://web_parser:8000/parse`.
4. Parser-service загружает страницу и достает `<title>`.
5. Основной backend получает результат.
6. Результат возвращается клиенту и может быть сохранен как todo.

Плюс этого варианта - простота. Минус - клиент ждет завершения парсинга.

## Асинхронный вызов через Celery

Для долгих операций используется очередь:

1. Клиент отправляет URL в `POST /parser/parse/start`.
2. FastAPI создает Celery task и сразу возвращает `task_id`.
3. Celery worker забирает задачу из Redis.
4. Worker вызывает сервис парсера.
5. Результат сохраняется в Redis.
6. Клиент запрашивает состояние и результат через `GET /parser/parse/result/{task_id}`.

Такой подход не блокирует HTTP-запрос пользователя и лучше подходит для операций, которые могут выполняться несколько секунд или дольше.

## Роли компонентов

| Компонент | Роль |
| --- | --- |
| FastAPI | Принимает HTTP-запросы и выдает `task_id` |
| Redis | Хранит очередь задач и результаты |
| Celery | Управляет выполнением фоновых задач |
| Celery worker | Выполняет парсинг вне процесса API |
| web_parser | Выполняет фактическое извлечение заголовка |

## Маршруты

| Метод | Путь | Назначение |
| --- | --- | --- |
| `POST` | `/parser/parse` | Синхронно распарсить URL и сохранить результат как todo |
| `POST` | `/parser/parse/start` | Поставить задачу парсинга в очередь Celery |
| `GET` | `/parser/parse/result/{task_id}` | Получить состояние и результат фоновой задачи |
| `POST` | `/parse` | Внутренний endpoint сервиса `web_parser` |

Тело запроса для парсинга:

```json
{
  "url": "https://example.com"
}
```

Ответ синхронного парсинга:

```json
{
  "url": "https://example.com/",
  "result": "Example Domain"
}
```

Ответ при постановке задачи в очередь:

```json
{
  "id": "celery-task-id",
  "state": "STARTED",
  "result": null
}
```

## Что важно понимать при защите

- Синхронный HTTP-вызов проще, но блокирует клиента до получения ответа.
- Celery позволяет вынести долгую операцию из request-response цикла.
- Redis в этой работе используется не как кэш, а как брокер и backend результатов.
- Docker Compose связывает контейнеры через внутреннюю сеть и имена сервисов.
- Отдельный parser-service уменьшает связанность основного API и логики парсинга.
