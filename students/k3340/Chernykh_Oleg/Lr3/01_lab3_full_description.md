# Лабораторная работа 3: подробное описание

## Общая идея

Лабораторная работа посвящена упаковке существующего FastAPI-приложения, базы данных и парсера в Docker, а также интеграции парсера с основным API двумя способами:

1. Синхронный вызов парсера через HTTP.
2. Асинхронный вызов парсера через очередь Celery и Redis.

До этой лабораторной уже должны быть готовы три части:

- FastAPI-приложение из лабораторной 1.
- База данных из лабораторной 1.
- Парсер данных из лабораторной 2.

В третьей лабораторной эти части нужно собрать в единую систему: каждый компонент запускается в отдельном контейнере, а общение между компонентами происходит по внутренней Docker-сети.

## Цель лабораторной

Цель: научиться разворачивать backend-систему как набор контейнеров и связывать между собой несколько сервисов:

- основной FastAPI backend;
- PostgreSQL;
- отдельный HTTP-сервис парсера;
- Redis;
- Celery worker.

Практический смысл работы в том, что реальные backend-приложения редко состоят из одного процесса. Обычно есть API, база данных, фоновые задачи, кэш или брокер сообщений, внешние сервисы. Docker Compose позволяет описать такую систему в одном файле и запускать ее одной командой.

## Что требуется по условию

### Подзадача 1. Упаковка FastAPI, базы данных и парсера в Docker

Нужно:

- создать Dockerfile для основного FastAPI-приложения;
- создать Dockerfile для приложения с парсером;
- добавить PostgreSQL как отдельный сервис;
- описать все сервисы в `docker-compose.yml` или `docker-compose.yaml`;
- настроить порты, переменные окружения, зависимости между сервисами и общую сеть;
- реализовать возможность вызова парсера по HTTP.

Минимальная архитектура:

```text
Клиент -> FastAPI приложение -> HTTP-запрос -> сервис парсера
                         |
                         v
                    PostgreSQL
```

### Подзадача 2. Вызов парсера из FastAPI

Нужно добавить в основной FastAPI backend эндпоинт, который:

1. Принимает URL от клиента.
2. Отправляет HTTP-запрос в контейнер с парсером.
3. Получает результат парсинга.
4. Возвращает результат клиенту.
5. При необходимости сохраняет результат в базу данных.

Важный момент: парсер находится не внутри основного приложения, а в отдельном контейнере. Поэтому основной backend обращается к нему по имени сервиса из Docker Compose, например `http://web_parser:8000/parse`.

### Подзадача 3. Вызов парсера через очередь

Для полного балла нужно добавить асинхронную обработку через Celery и Redis.

Нужно:

- добавить зависимости `celery` и `redis`;
- настроить Celery-приложение;
- создать Celery task для парсинга URL;
- добавить Redis как брокер сообщений и backend результатов;
- добавить Celery worker как отдельный сервис в Docker Compose;
- добавить эндпоинт для постановки задачи в очередь;
- добавить эндпоинт для получения результата по `task_id`.

Архитектура становится такой:

```text
Клиент -> FastAPI -> Redis queue -> Celery worker -> HTTP -> parser
   ^         |                                                |
   |         v                                                v
   +---- task_id / result                              parsed title
```

## Зачем нужен Docker

Docker решает проблему различий между окружениями. Без Docker приложение зависит от локально установленного Python, PostgreSQL, Redis, системных библиотек и переменных окружения. На другой машине все может работать иначе.

Контейнер фиксирует окружение:

- базовый образ, например `python:3.13-slim`;
- системные зависимости;
- Python-зависимости;
- рабочую директорию;
- команду запуска.

Итог: приложение можно собрать в образ и запускать одинаково на разных машинах.

## Зачем нужен Docker Compose

Docker запускает один контейнер. Docker Compose управляет несколькими связанными контейнерами.

В этой лабораторной Compose нужен, потому что система состоит минимум из нескольких сервисов:

- `todo_app`;
- `web_parser`;
- `postgres`;
- `redis`;
- `celery_worker`.

Compose позволяет:

- описать все сервисы в одном YAML-файле;
- поднять всю систему командой `docker compose up`;
- создать общую сеть;
- подключить volumes для хранения данных;
- указать зависимости через `depends_on`;
- настроить переменные окружения.

## Зачем отделять парсер от основного API

Парсер может быть долгой или тяжелой операцией:

- он делает сетевой запрос к внешнему сайту;
- ждет ответ;
- разбирает HTML;
- может упасть из-за недоступного сайта;
- может работать значительно дольше обычного API-запроса.

Если держать парсер внутри основного API, то backend будет сильнее связан с этой логикой. Отдельный сервис парсера дает более чистую архитектуру:

- основной API отвечает за пользователей, авторизацию, todo и публичные маршруты;
- parser-service отвечает только за извлечение данных из URL;
- компоненты можно масштабировать отдельно;
- парсер можно заменить, не переписывая весь backend.

## Зачем нужна очередь

Синхронный HTTP-вызов прост, но клиент должен ждать, пока парсер закончит работу. Если парсинг длится 15 секунд, HTTP-запрос тоже будет висеть 15 секунд.

Очередь решает это так:

1. Клиент отправляет URL.
2. FastAPI быстро кладет задачу в Redis.
3. FastAPI сразу возвращает `task_id`.
4. Celery worker забирает задачу из Redis и выполняет ее в фоне.
5. Клиент позднее запрашивает результат по `task_id`.

Это повышает отзывчивость API и позволяет выполнять долгие операции без блокировки клиентского запроса.

## Теоретический минимум

### FastAPI

FastAPI - Python-фреймворк для создания HTTP API. Важные понятия:

- `FastAPI()` создает приложение;
- `APIRouter` группирует маршруты;
- `@router.get`, `@router.post` описывают endpoints;
- Pydantic-модели валидируют входные и выходные данные;
- `Depends` подключает зависимости, например текущего пользователя или HTTP-сессию;
- `HTTPException` возвращает управляемую ошибку API.

### HTTP и REST

Основной обмен между сервисами идет через HTTP:

- `POST /parse` отправляет URL на парсинг;
- тело запроса содержит JSON;
- ответ тоже приходит в JSON;
- коды состояния показывают результат: `200`, `400`, `401`, `500` и так далее.

### Pydantic

Pydantic используется для схем:

- проверяет, что URL действительно похож на URL;
- описывает формат ответа;
- помогает FastAPI автоматически генерировать документацию Swagger.

### PostgreSQL

PostgreSQL хранит данные приложения. В этой работе база запускается в отдельном контейнере. Данные не пропадают после перезапуска благодаря Docker volume.

### ORM и миграции

В решении используется Tortoise ORM и Aerich:

- Tortoise ORM связывает Python-модели с таблицами базы;
- Aerich применяет миграции;
- `entrypoint.sh` перед запуском приложения выполняет `aerich upgrade`.

### Redis

Redis в этой лабораторной используется не как обычный кэш, а как брокер задач и хранилище результатов Celery.

Брокер - это посредник между API и worker:

- FastAPI кладет задачу в Redis;
- Celery worker забирает ее;
- результат сохраняется обратно в Redis.

### Celery

Celery - система фоновых задач. Основные понятия:

- Celery app - объект с настройками брокера и backend;
- task - функция, которую можно выполнить в фоне;
- worker - отдельный процесс, который слушает очередь;
- `delay()` ставит задачу в очередь;
- `AsyncResult(task_id)` позволяет узнать состояние и результат.

Типичные состояния Celery task:

- `PENDING` - задача еще не обработана или результат неизвестен;
- `STARTED` - задача начата, если включено отслеживание старта;
- `SUCCESS` - задача завершилась успешно;
- `FAILURE` - задача завершилась ошибкой.

### Async, threading и multiprocessing

В условии отдельно упоминается понимание `threading`, `multiprocessing` и `async`.

Кратко:

- `async` хорошо подходит для большого числа операций ввода-вывода: HTTP-запросы, работа с сетью, ожидание ответа;
- `threading` запускает несколько потоков внутри одного процесса, удобно для I/O, но в Python ограничено GIL для CPU-bound задач;
- `multiprocessing` запускает отдельные процессы, полезно для CPU-bound задач, потому что каждый процесс имеет свой интерпретатор Python;
- Celery обычно запускает отдельные worker-процессы и позволяет выносить тяжелые задачи из основного API.

В этой работе:

- FastAPI routes написаны асинхронно;
- `aiohttp` используется для неблокирующих HTTP-запросов;
- Celery worker выполняет фоновую задачу отдельно от FastAPI;
- Redis связывает FastAPI и worker.

## Что считается хорошим результатом

Хорошее решение показывает, что:

- приложение и парсер упакованы в Docker;
- база данных запускается в контейнере;
- все сервисы описаны в Docker Compose;
- основной API может вызвать парсер по HTTP;
- есть асинхронный запуск через Celery;
- Redis используется как брокер и backend результатов;
- пользователь может получить `task_id`, а затем результат;
- результат парсинга интегрирован с бизнес-логикой приложения, например сохраняется как todo.
