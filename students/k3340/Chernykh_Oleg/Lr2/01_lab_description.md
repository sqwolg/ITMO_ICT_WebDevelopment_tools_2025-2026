# Лабораторная работа 2. Потоки. Процессы. Асинхронность

## 1. Что требуется сделать

Лабораторная работа посвящена сравнению трех способов конкурентного выполнения задач в Python:

- `threading` - выполнение нескольких потоков внутри одного процесса;
- `multiprocessing` - выполнение нескольких процессов;
- `asyncio` - асинхронное выполнение задач в одном потоке через цикл событий.

В работе две практические задачи.

### Задача 1. Подсчет суммы большого диапазона

Нужно написать три отдельные программы, каждая из которых считает сумму чисел в большом диапазоне:

- вариант на `threading`;
- вариант на `multiprocessing`;
- вариант на `asyncio`.

В каждой программе должна быть функция `calculate_sum()`. Диапазон должен делиться на несколько частей, каждая часть должна обрабатываться отдельной задачей, потоком или процессом. После этого частичные суммы объединяются в общий результат. Также нужно измерить время выполнения и сравнить подходы.

В условии указан диапазон до `10_000_000_000_000`. В текущем решении используется `1_000_000_000`, потому что такой запуск реалистичнее продемонстрировать на обычной машине. Логика разбиения задачи при этом такая же: меняется только верхняя граница.

### Задача 2. Параллельный парсинг с сохранением в базу данных

Нужно написать еще три программы:

- парсинг через `threading`;
- парсинг через `multiprocessing`;
- парсинг через `asyncio` и `aiohttp`.

Каждая программа должна содержать функцию `parse_and_save(url)`. Она должна загрузить данные по URL, разобрать ответ, сохранить полученные данные в базу данных и вывести результат на экран.

По условию нужно использовать базу данных из лабораторной работы 1. В решении используется таблица `todos`, модель `Todo` и SQLAlchemy. Данные берутся из API `https://dummyjson.com/todos`.

Дополнительно требуется оформить документацию:

- описать каждую программу;
- объяснить особенности подходов;
- привести таблицы с временем выполнения;
- прокомментировать результаты.

## 2. Зачем это нужно

Главная цель лабораторной - понять, что "параллельно" в Python может означать разные вещи.

Одна и та же задача может быть:

- вычислительной, то есть нагружать CPU;
- сетевой или дисковой, то есть большую часть времени ждать ответа от внешнего ресурса.

Для этих двух типов задач подходят разные инструменты.

Для тяжелых вычислений лучше подходит `multiprocessing`, потому что несколько процессов могут реально выполняться на разных ядрах процессора. Для сетевых запросов часто лучше подходят `threading` или `asyncio`, потому что пока один запрос ждет ответ, программа может заниматься другими запросами.

Эта тема важна для backend-разработки: серверы постоянно работают с запросами, базами данных, файлами, внешними API и очередями задач. Нужно понимать, где достаточно асинхронности, где выгодны потоки, а где нужны процессы.

## 3. Теоретический минимум

### Процесс

Процесс - это отдельный экземпляр выполняемой программы. У процесса есть собственная память, свои ресурсы и свой интерпретатор Python.

Плюсы процессов:

- можно использовать несколько ядер CPU;
- процессы изолированы друг от друга;
- хорошо подходят для CPU-bound задач.

Минусы процессов:

- создание процесса дороже, чем создание потока;
- у процессов разная память, поэтому сложнее обмениваться данными;
- нужно передавать данные между процессами, что дает накладные расходы.

### Поток

Поток - это линия выполнения внутри процесса. Несколько потоков одного процесса используют общую память.

Плюсы потоков:

- легче процессов;
- удобно использовать для сетевых запросов и ожидания I/O;
- потоки могут работать с общими переменными.

Минусы потоков:

- из-за общей памяти возможны гонки данных;
- для защиты общих данных нужны блокировки;
- в CPython есть GIL, который мешает нескольким потокам одновременно выполнять Python-код на CPU.

### GIL

GIL, или Global Interpreter Lock, - это глобальная блокировка интерпретатора CPython. Она не дает нескольким потокам одновременно выполнять Python bytecode в одном процессе.

Из-за GIL потоки плохо ускоряют CPU-bound задачи, например большой подсчет суммы. Даже если потоков несколько, Python-код фактически выполняется по очереди.

При этом GIL не мешает потокам быть полезными для I/O-bound задач. Когда поток ждет сеть, файл или базу данных, другой поток может продолжить работу.

### Асинхронность

Асинхронность в Python обычно строится на `asyncio`. Программа работает в одном потоке, а переключение между задачами происходит в моменты `await`.

Основные понятия:

- `async def` объявляет корутину;
- `await` передает управление циклу событий, пока операция не завершилась;
- `asyncio.gather()` запускает несколько корутин конкурентно;
- `asyncio.run()` создает цикл событий и запускает главную корутину.

Асинхронность особенно полезна для I/O-bound задач: HTTP-запросов, работы с базой, ожидания файловых операций. Но она не ускоряет обычные CPU-вычисления, если внутри корутины нет реального ожидания.

### CPU-bound и I/O-bound

CPU-bound задача ограничена скоростью процессора. Пример из лабораторной: подсчет суммы большого диапазона.

I/O-bound задача ограничена ожиданием ввода-вывода. Пример из лабораторной: загрузка данных с сайта и запись в базу данных.

Общее правило:

| Тип задачи | Обычно лучше подходит |
| --- | --- |
| CPU-bound | `multiprocessing` |
| I/O-bound с синхронными библиотеками | `threading` |
| I/O-bound с асинхронными библиотеками | `asyncio` |

## 4. Что проверяется в этой лабораторной

Преподаватель, скорее всего, смотрит не только на факт запуска программ, но и на понимание:

- чем поток отличается от процесса;
- почему `threading` не ускоряет тяжелые вычисления в CPython;
- почему `multiprocessing` быстрее в задаче с суммой;
- почему `asyncio` хорошо подходит для сетевого парсинга;
- зачем нужна блокировка `Lock` при общей переменной;
- как `Pool` распределяет задачи между процессами;
- что делает `asyncio.gather()`;
- почему для async-версии HTTP используется `aiohttp`, а не `requests`;
- почему для async-версии БД используется `AsyncSession`;
- какие накладные расходы есть у каждого подхода.

## 5. Ожидаемые результаты сравнения

Для подсчета суммы ожидаемая картина такая:

- `multiprocessing` быстрее, потому что использует несколько процессов и несколько ядер;
- `threading` медленнее из-за GIL;
- `asyncio` не дает выигрыша, потому что внутри нет неблокирующего ожидания.

Для парсинга ожидаемая картина другая:

- `asyncio` часто быстрее, потому что запросы выполняются неблокирующе;
- `threading` тоже хорошо подходит, потому что сетевой ввод-вывод освобождает поток ожидания;
- `multiprocessing` может быть медленнее из-за дорогого создания процессов и отдельных подключений к БД.
