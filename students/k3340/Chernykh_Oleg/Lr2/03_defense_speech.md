## Короткое вступление

Здравствуйте. В этой лабораторной работе я сравнивал три способа конкурентного выполнения задач в Python: `threading`, `multiprocessing` и `asyncio`.

Цель была понять, чем отличаются потоки, процессы и асинхронность, и на практике увидеть, какой подход лучше подходит для вычислительных задач, а какой - для задач с ожиданием сети и базы данных.

В работе две части. В первой части я считал сумму большого диапазона чисел. Это CPU-bound задача. Во второй части я параллельно загружал данные с API `dummyjson.com`, разбирал их и сохранял в таблицу `todos` в базе данных. Это I/O-bound задача.

## Рассказ про задачу 1

В первой задаче нужно было посчитать сумму большого диапазона. Я разбил диапазон на 4 части. Каждая часть считается отдельно, потом частичные суммы объединяются.

В `thread.py` я использую модуль `threading`. На каждую часть диапазона создается поток. У потоков общая переменная `result`, поэтому для ее изменения я использую `threading.Lock`. Блокировка нужна, чтобы два потока одновременно не изменили общую сумму и не потеряли часть результата.

Здесь важно, что потоки в CPython не дают настоящего ускорения для CPU-bound задач из-за GIL. Поэтому результат по времени получился не лучшим.

Дальше я показываю `process.py`. Здесь используется `multiprocessing.Pool`. Диапазон тоже делится на части, но каждая часть считается в отдельном процессе. У каждого процесса свой интерпретатор и свой GIL, поэтому процессы могут реально работать на разных ядрах. Для вычислительной задачи это самый подходящий вариант, и он показал лучшее время.

Потом я показываю `async.py`. Там используются `async def`, `asyncio.gather()` и `asyncio.run()`. Но эта задача не подходит для асинхронности, потому что внутри корутин нет ожидания сети или файла, а есть обычное вычисление. Поэтому `asyncio` здесь не дает реального ускорения.

Вывод по первой задаче: для CPU-bound задач лучше использовать `multiprocessing`.

## Рассказ про задачу 2

Во второй задаче нужно было параллельно получить данные с нескольких URL и сохранить их в базу данных.

Я использую список URL:

```python
URLS = [f"https://dummyjson.com/todos?skip={i}&limit=25" for i in range(0, 251, 25)]
```

Каждый URL возвращает часть списка задач. Из ответа я беру поле `todos`, а затем сохраняю каждую задачу в таблицу `todos`.

В `database.py` описана модель:

```python
class Todo(Base):
    __tablename__ = 'todos'
    id = Column(Integer, primary_key=True)
    title = Column(String, nullable=False)
    completed = Column(Boolean)
```

Также там есть синхронное подключение через `create_engine` и асинхронное подключение через `create_async_engine`. Это нужно, потому что `threading` и `multiprocessing` используют обычные SQLAlchemy-сессии, а async-версия использует `AsyncSession`.

В `task2/thread.py` я создаю отдельный поток на каждый URL. Каждый поток делает `requests.get`, разбирает JSON, открывает свою сессию БД, сохраняет данные и закрывает сессию. Для сетевых задач потоки подходят лучше, чем для вычислительных, потому что во время ожидания ответа другие потоки могут продолжать работу.

В `task2/process.py` я использую `multiprocessing.Pool` и распределяю URL между процессами. Это тоже работает, но для сетевой задачи процессы имеют слишком большие накладные расходы: создание процессов, отдельные подключения и память. Поэтому результат оказался хуже, чем у потоков и async.

В `task2/async.py` используется `aiohttp.ClientSession` и `asyncio.gather`. Все запросы запускаются конкурентно, и когда один запрос ждет ответ, event loop переключается на другие задачи. Для сохранения в БД используется `AsyncSession`. Поэтому async-версия получилась самой быстрой во второй задаче.

Вывод по второй задаче: для I/O-bound задач лучше всего подходит `asyncio`, если используются асинхронные библиотеки.

## Основные фишки решения

Главная фишка первой задачи - один и тот же алгоритм реализован тремя способами, поэтому можно честно сравнить именно модель конкурентности.

Вторая фишка - в задаче с потоками используется `Lock`, то есть учтена проблема общей памяти и race condition.

Третья фишка - в multiprocessing варианте используется `Pool`, а не ручное создание процессов. Это компактнее и лучше подходит для распределения однотипных задач.

Четвертая фишка - для async-парсинга используется не синхронный `requests`, а правильная асинхронная библиотека `aiohttp`.

Пятая фишка - для базы данных есть два режима работы: синхронный и асинхронный. Это важно, потому что async-код должен использовать async-драйвер и async-сессии.

Шестая фишка - используется `session.merge()`, поэтому повторный запуск не ломается из-за уже существующих `id` в таблице.

## Финальный вывод

По результатам лабораторной видно, что нет универсально лучшего подхода.

Для вычислений лучше подходит `multiprocessing`, потому что он обходит ограничение GIL и использует несколько ядер.

Для сетевых задач лучше подходят `threading` и особенно `asyncio`, потому что они позволяют эффективно использовать время ожидания ответов от внешних сервисов и базы данных.
