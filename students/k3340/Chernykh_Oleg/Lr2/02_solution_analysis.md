# Подробный разбор решения

## 1. Общая структура решения

Лабораторная находится в папке `Lr2` и разделена на две части:

- `task1` - подсчет суммы большого диапазона;
- `task2` - параллельный парсинг данных и сохранение в БД;
- `docs` - уже подготовленная документация для MkDocs.

В каждой задаче есть три реализации:

- `thread.py` - вариант на потоках;
- `process.py` - вариант на процессах;
- `async.py` - вариант на асинхронности.

В `task2` дополнительно есть `database.py`, где описано подключение к БД и модель таблицы `todos`.

## 2. Базовое объяснение задачи 1

В задаче 1 нужно посчитать сумму чисел от начала диапазона до верхней границы. В коде используется:

```python
TOTAL = 1_000_000_000
```

Затем диапазон делится на 4 части:

```python
CHUNK_SIZE = TOTAL // 4
```

Каждая часть считается отдельно. В конце частичные суммы складываются.

Функция:

```python
def range_sum(start, end):
    return sum(range(start, end))
```

считает сумму на полуинтервале `[start, end)`: `start` включается, `end` не включается. Поэтому при `TOTAL = 1_000_000_000` фактически считается сумма от `0` до `999_999_999`. Результат:

```text
499999999500000000
```

Это соответствует формуле суммы `0 + 1 + ... + (n - 1) = n * (n - 1) / 2`.

## 3. Task 1: threading

Файл: `task1/thread.py`.

В этой реализации создаются 4 потока:

```python
NUM_THREADS = 4
```

Каждый поток вызывает:

```python
partial_sum(start, end)
```

Сначала поток считает локальную сумму:

```python
local_sum = range_sum(start, end)
```

Потом добавляет ее в общую переменную `result`:

```python
with lock:
    result += local_sum
```

### Зачем нужен `Lock`

`result` - общая переменная для всех потоков. Если несколько потоков одновременно начнут ее менять, может возникнуть race condition: один поток прочитал старое значение, второй тоже прочитал старое значение, оба записали результат, и часть суммы потерялась.

`threading.Lock()` делает критическую секцию:

```python
with lock:
    result += local_sum
```

Внутрь этой секции одновременно может войти только один поток.

### Почему threading не лучший для этой задачи

Подсчет суммы - CPU-bound задача. Она нагружает процессор, а не ждет сеть или диск. В CPython потоки ограничены GIL, поэтому несколько потоков не выполняют Python-код на CPU одновременно. Из-за этого ускорение небольшое или его нет.

## 4. Task 1: multiprocessing

Файл: `task1/process.py`.

Здесь используется пул из 4 процессов:

```python
with multiprocessing.Pool(NUM_PROCESSES) as pool:
```

Для каждого процесса создается пара `(start, end)`:

```python
ranges = [
    (i * CHUNK_SIZE, TOTAL if i == NUM_PROCESSES - 1 else (i + 1) * CHUNK_SIZE)
    for i in range(NUM_PROCESSES)
]
```

Затем `pool.starmap()` вызывает `range_sum(start, end)` для каждой пары аргументов:

```python
results = pool.starmap(range_sum, ranges)
```

В конце результаты процессов складываются:

```python
return sum(results)
```

### Почему multiprocessing быстрее

Каждый процесс имеет отдельный интерпретатор Python и отдельный GIL. Поэтому разные процессы могут реально выполняться на разных ядрах CPU. Для вычислительной задачи это самый подходящий вариант из трех.

В документации зафиксировано время:

| Подход | Время |
| --- | --- |
| Multiprocessing | 5.9216 с |

### Важный момент

У `multiprocessing` есть накладные расходы:

- создание процессов;
- передача аргументов в процессы;
- получение результатов обратно;
- отдельная память у каждого процесса.

Но для большой CPU-bound задачи выигрыш от нескольких ядер перекрывает эти расходы.

## 5. Task 1: asyncio

Файл: `task1/async.py`.

Вариант использует корутины:

```python
async def partial_sum(start, end):
    return range_sum(start, end)
```

Все корутины собираются через:

```python
results = await asyncio.gather(*tasks)
```

### Почему asyncio здесь почти не ускоряет

`asyncio` дает конкурентность только там, где корутина делает `await` на неблокирующей операции. Например, HTTP-запрос через `aiohttp` или запрос к БД через async-драйвер.

В задаче с суммой внутри корутины выполняется обычный синхронный CPU-код:

```python
return range_sum(start, end)
```

Пока эта функция считает сумму, цикл событий не может переключиться на другую корутину. Поэтому корутины фактически выполняются последовательно.

## 6. Базовое объяснение задачи 2

Во второй задаче нужно загрузить данные с нескольких URL и сохранить их в БД.

Список URL формируется так:

```python
URLS = [f"https://dummyjson.com/todos?skip={i}&limit=25" for i in range(0, 251, 25)]
```

Получается 11 адресов:

- `skip=0`;
- `skip=25`;
- `skip=50`;
- ...
- `skip=250`.

Каждый URL возвращает JSON со списком задач `todos`. Обычно приходит 25 записей, а в последнем запросе меньше, потому что данные заканчиваются.

Каждый элемент сохраняется в таблицу `todos`:

```python
Todo(id=todo["id"], title=todo["todo"], completed=todo["completed"])
```

Используется `session.merge(t)`, а не просто `add(t)`. Это полезно для повторного запуска: если запись с таким `id` уже есть, она обновляется, а не вызывает ошибку первичного ключа.

## 7. База данных

Файл: `task2/database.py`.

В файле описаны две версии подключения:

- синхронная:

```python
engine = create_engine(DATABASE_URL)
SessionLocal = sessionmaker(bind=engine)
```

- асинхронная:

```python
async_engine = create_async_engine(DATABASE_URL_ASYNC, echo=False)
AsyncSessionLocal = sessionmaker(async_engine, expire_on_commit=False, class_=AsyncSession)
```

Адреса подключения берутся из переменных окружения:

```python
DATABASE_URL = os.getenv("DB_URL")
DATABASE_URL_ASYNC = os.getenv("DB_ASYNC_URL")
```

Модель:

```python
class Todo(Base):
    __tablename__ = 'todos'

    id = Column(Integer, primary_key=True)
    title = Column(String, nullable=False)
    completed = Column(Boolean)
```

Функция `init_db()` создает таблицу в синхронном варианте, а `async_init_db()` - в асинхронном.

## 8. Task 2: threading

Файл: `task2/thread.py`.

На каждый URL создается отдельный поток:

```python
t = threading.Thread(target=parse_and_save, args=(url,))
```

Функция `parse_and_save(url)`:

1. выполняет HTTP-запрос через `requests.get(url)`;
2. разбирает JSON;
3. открывает SQLAlchemy-сессию;
4. сохраняет записи через `merge`;
5. делает `commit`;
6. закрывает сессию.

Этот подход хорошо подходит для сетевых запросов, потому что пока один поток ждет ответ от API или БД, другие потоки могут работать.

## 9. Task 2: multiprocessing

Файл: `task2/process.py`.

Здесь используется пул процессов:

```python
with multiprocessing.Pool(processes=4) as pool:
    pool.map(parse_and_save, URLS)
```

`pool.map()` распределяет URL между процессами. Каждый процесс самостоятельно выполняет запрос, открывает сессию БД и сохраняет данные.

### Почему multiprocessing здесь может быть медленнее

Парсинг URL - I/O-bound задача. Основное время уходит на ожидание сети и базы данных, а не на вычисления CPU. Процессы дают настоящий параллелизм, но цена за него выше:

- нужно создать несколько процессов;
- у каждого процесса отдельная память;
- у каждого процесса отдельная работа с подключениями к БД;
- обмен задачами между главным процессом и рабочими процессами тоже стоит времени.

Поэтому в сетевой задаче `multiprocessing` может проигрывать `threading` и `asyncio`.

## 10. Task 2: asyncio

Файл: `task2/async.py`.

Асинхронная версия использует:

- `aiohttp.ClientSession()` для HTTP;
- `AsyncSessionLocal()` для БД;
- `asyncio.gather()` для конкурентного запуска всех запросов.

Главная функция:

```python
async def main():
    await async_init_db()
    async with aiohttp.ClientSession() as session_http:
        tasks = [parse_and_save(session_http, url) for url in URLS]
        await asyncio.gather(*tasks)
```

`ClientSession` создается один раз и переиспользуется для всех запросов. Это правильно, потому что сессия управляет соединениями и уменьшает накладные расходы.

В `parse_and_save` есть несколько важных `await`:

```python
async with session_http.get(url) as response:
    data = await response.json()
```

и:

```python
await db_session.merge(t)
await db_session.commit()
```

Когда корутина ждет HTTP-ответ или БД, цикл событий может переключиться на другую корутину. Поэтому этот подход хорошо работает для сетевых задач.

## 12. Места, на которые стоит обратить внимание при сдаче

1. В условии для задачи 1 указан больший диапазон, чем в коде. Лучше честно сказать, что в реализации выбран `1_000_000_000` для практической демонстрации времени запуска, но архитектура решения не меняется при увеличении `TOTAL`.

2. В задаче 1 код считает от `0` до `TOTAL - 1`, а не от `1` до `TOTAL`. Для сравнения подходов это не критично, потому что нагрузка и принцип разбиения такие же. Если нужно строго по условию, старт первого диапазона можно сделать `1`, а последнюю границу `TOTAL + 1`.

3. `threading.Lock` нужен только там, где несколько потоков меняют общую переменную. В multiprocessing варианте общей переменной нет: процессы возвращают результаты, а главный процесс складывает их.

4. `asyncio` не равно параллельное выполнение на нескольких ядрах. Это конкурентность в одном потоке, эффективная при ожидании I/O.

5. `requests` - синхронная библиотека. Поэтому в async-версии используется `aiohttp`.

6. Для async-версии БД нужна асинхронная SQLAlchemy-сессия и async-драйвер, поэтому есть отдельная переменная `DB_ASYNC_URL`.

7. `session.merge()` делает повторный запуск безопаснее, потому что обновляет существующие строки по первичному ключу.
